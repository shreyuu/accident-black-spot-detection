# Engineering Decisions

Why the code looks the way it does. `flow.md` is the companion document and
explains **how** the system executes; this one explains **why** it is shaped
that way.

## Scope of this file

This log begins partway through the project's life. Phases 0–14 predate it, and
their reasoning was recorded in three other places that remain authoritative for
that period and are **not** duplicated here:

- [`docs/adr/0001-platform-and-stack.md`](docs/adr/0001-platform-and-stack.md) —
  the stack decision and what was rejected.
- [`docs/`](docs/) — one document per subsystem, each explaining the trade-offs
  in its area (`security-and-privacy.md`, `background-monitoring.md`,
  `eclat-methodology.md`, `settings-and-offline.md`, `nearby-places.md`).
- Source comments. This codebase deliberately documents _why_ at the point of
  the decision, and those comments are frequently the fullest account that
  exists. `firebase/firestore.rules` and
  `apps/mobile/src/features/alerts/zoneStatePersistence.ts` are the clearest
  examples.

Decisions from DEC-001 onwards are recorded here as they are made. Where an
entry restates something already argued in a source comment, it links to it
rather than copying it, so the two cannot drift.

## DEC-001 — Untrack the root-level Expo prebuild rather than adopt it

**Date:** 2026-08-10
**Status:** Active
**Affected Areas:** `/ios/` (removed), `/app.json` (removed), `package.json`,
`.gitignore`, `scripts/nativeBuildOutput.mjs`, `scripts/checkNativeBuildOutput.mjs`

### Context

Commit `cbd8a2d` added a full Xcode project at the repository root, a second
`app.json`, and `expo`/`react`/`react-native` to the root `package.json`
dependencies. This was an `expo prebuild` run from the repository root instead of
from `apps/mobile`.

Three identities for one app existed as a result:

| Location                           | Bundle identifier                             | Version |
| ---------------------------------- | --------------------------------------------- | ------- |
| `apps/mobile/app.config.ts` (real) | `com.shreyuu.accidentblackspotdetection`      | `0.1.0` |
| `/app.json` (stray)                | `com.anonymous.accident-black-spot-detection` | —       |
| `/ios/…/project.pbxproj` (stray)   | `org.name.accidentblackspotdetection`         | `1.0`   |

The latter two are Expo template defaults — nothing generated them from this
project's configuration. `docs/ios-device-builds.md` documents the real device
build as `apps/mobile/ios/AccidentBlackSpotDetectionDev.xcworkspace`, which
`expo run:ios` regenerates and which `.gitignore` already excluded.

### Decision

Untrack both paths (`git rm -r --cached ios app.json`), remove the three root
dependencies, extend `.gitignore` to `/ios/` and `/android/`, and add a
tracked-path guard to the `test:scripts` gate.

### Reasoning

The directory is generated output that contradicts the project's own stated
policy — `.gitignore` says "Generated by `expo prebuild` — regenerate, never
commit". Nothing referenced it. Keeping it would mean maintaining a second
native project whose identity matches nothing, and inviting a contributor to
open the wrong Xcode workspace.

`--cached` rather than a plain `git rm` leaves the working-tree files in place,
so the removal is reversible without touching git history.

### Alternatives Considered

#### Adopt the root prebuild as the real one

Move the app's identity to match it and build from the root. Rejected: the app
lives in `apps/mobile` as an npm workspace, `app.config.ts` is a dynamic config
that generates native projects correctly, and the root project was a bare
template that had never had the config plugins applied — its `Info.plist`
declares no `UIBackgroundModes` at all, so background monitoring could not work.

#### Untrack, and also add `/app.json` to `.gitignore`

Rejected deliberately. See the trade-off below; this is the decision's most
debatable point.

#### Leave it and add a README note

Rejected. A note does not stop `git add -A`, and the failure it prevents is
somebody building the wrong thing and not understanding why it behaves oddly.

### Trade-offs

Benefits:

- One app identity, matching the documented build.
- The guard makes any recurrence a build failure rather than a silent addition.

Costs / disadvantages:

- `/app.json` is **not** gitignored, so it shows as `?? app.json` in
  `git status` until the on-disk file is deleted, and `git add -A` would
  re-add it.

That cost is accepted on purpose. The reason the original commit went unnoticed
is that every gate was scoped to `apps/mobile/` — `.gitignore`, `.prettierignore`
and ESLint alike — so thirteen files entered the repository with nothing holding
an opinion. An ignore rule that is wrong is silent, and silence is the failure
mode being fixed. A guard that fails loudly and names the file is preferred to a
rule that hides it.

### Consequences

`npm run test:scripts` now runs `scripts/checkNativeBuildOutput.mjs`, which reads
`git ls-files` and fails on any tracked path under `ios/`, `android/`,
`apps/mobile/ios/`, `apps/mobile/android/`, `functions/lib/`, or a root
`app.json`. Detection logic is pure and unit-tested in
`scripts/nativeBuildOutput.mjs`, mirroring the `workflowParity.mjs` split.

Removing the root dependencies changed no lockfile entry — `npm ci` was verified
to succeed both before and after, so CI was never broken by the mismatch.

### Revisit When

The app moves out of `apps/mobile`, or a legitimate root-level `app.json` is
needed. Either means editing `FORBIDDEN` in `scripts/nativeBuildOutput.mjs`,
which is the intended place for that argument to happen.

## DEC-002 — Require a verified email address to create a report, and nothing else

**Date:** 2026-08-10
**Status:** Active
**Affected Areas:** `firebase/firestore.rules`, `firebase/tests/helpers.mjs`,
`firebase/tests/ownership.test.mjs`, `apps/mobile/src/features/auth/authService.ts`,
`apps/mobile/src/features/reports/EmailVerificationGate.tsx`,
`apps/mobile/app/(tabs)/report.tsx`, `firebase/scripts/confirmEmail.mjs`

### Context

Report submission is rate limited to ten per twenty-four hours **per account**
(DEC-pre-existing; see `docs/security-and-privacy.md` §2). The limit is exactly
enforced and every bypass is closed — but it is bounded by nothing scarce,
because Firebase Auth accepts any address without checking it. The price of ten
more submissions was one more sign-up.

The resource being protected is a human moderator. It is the only thing in the
system that does not scale, and exhausting it means genuine reports go unread.

### Decision

Add `hasVerifiedEmail()` to `firestore.rules` and require it on
`incidentReports` **create only**. The mobile app sends a verification email on
registration and shows a gate in place of the report form when the address is
unconfirmed.

### Reasoning

Enforced in the rules because that is the only place it binds — the client check
is a courtesy that avoids letting somebody write a description, place a pin and
upload a photograph before learning the write was never going to succeed.

`request.auth.token.get('email_verified', false)` rather than a truthiness
check: a token from a provider that never sets the claim must read as _not
verified_ rather than raise. An erroring rule is a denial for the wrong reason,
and it takes the rest of the evaluation with it — which is exactly how the Phase
13 `hasNoPrivilegedFields` bug behaved.

### Alternatives Considered

#### Firebase App Check

The stronger control: it attests that the request comes from a genuine build.
Not chosen _now_ because it requires a real Firebase project, and this project
has only ever run against emulators. It remains the right long-term answer and
is recorded as a gap in `docs/security-and-privacy.md` §7.

#### Gate every write behind verification

Rejected on safety grounds. Someone in an emergency must never be told to check
their email before using SOS or adding an emergency contact. Those writes also
touch only the caller's own documents, so there is no abuse case to answer.

#### Enforce only in the client

Rejected outright. The rules are the enforcement point; a client check is
advisory and this project's standing rule is to validate at both boundaries.

#### A CAPTCHA or phone verification

Rejected: heavier, and phone verification costs money per verification in a
project that deliberately has no billing account.

### Trade-offs

Benefits:

- An account now costs a working inbox rather than nothing.
- No new dependency, no new service, one rule clause.

Costs / disadvantages:

- **It is a floor, not a wall.** Disposable-address services defeat it. It
  changes abuse from free to fiddly and no more than that.
- Adds a step to the demo flow, since the Auth emulator delivers no mail.
- The claim lives inside the ID token, so an account that verifies while signed
  in keeps being refused until the token is refreshed. This is the most
  confusing part of the feature and needed dedicated UI.

### Consequences

`asUser`/`asModerator`/`asAdmin` in `firebase/tests/helpers.mjs` now issue
`email_verified: true`, because they stand for established accounts. A new
`asUnverifiedUser` makes the negative case something a test has to ask for
explicitly, rather than something every report test trips over by accident.

`refreshEmailVerification()` in `authService.ts` calls `user.reload()` then
`user.getIdToken(true)` — in that order — and is wired to the gate's "I have
confirmed my address" button.

`npm run confirm-email` was added for the demo. The emulator's real verification
link also works and is documented in `docs/demo.md`; the script is the shortcut
for repeat runs. Both are guarded against running against a real project.

### Revisit When

App Check becomes available, or evidence appears that verification is blocking
legitimate reporting more than it is deterring abuse. If the gate is ever
widened beyond report creation, the tests asserting the SOS and emergency-contact
exclusions must be updated deliberately — they exist to make that a conscious act.

## DEC-003 — Record background-task run outcomes on-device, without location data

**Date:** 2026-08-10
**Status:** Active
**Affected Areas:** `apps/mobile/src/features/alerts/backgroundRunHealth.ts`,
`backgroundRunHealthStore.ts`, `backgroundRunCopy.ts`, `useBackgroundRunHealth.ts`,
`backgroundLocationTask.ts`, `apps/mobile/app/(tabs)/settings.tsx`,
`apps/mobile/src/features/auth/AuthProvider.tsx`

### Context

The background proximity task is the only part of the app whose failure is
silent. It has no UI, no user watching and no caller to return to, and its
failure mode — no warning arrives — is indistinguishable from "there was nothing
to warn about". Settings said "active" whether or not the OS was still
scheduling it.

`logger.ts` carried a `TODO(phase-14)` to forward to a crash reporter, unresolved.

### Decision

Record one entry per invocation — an outcome label and a timestamp — to
AsyncStorage, and surface a summary on the Settings screen when background
monitoring is active. No crash reporter.

### Reasoning

The question worth answering is "did the task run", and that needs no vendor. A
counter on disk answers it, works offline, adds no dependency, and sends nothing
anywhere — which matters for a feature whose data is movement-shaped.

The outcome is recorded at every exit point of `handleBackgroundLocations`,
because a path that returns without recording is indistinguishable from a task
the OS never started, which is the condition the record exists to expose.

### Alternatives Considered

#### Sentry or Firebase Crashlytics

Rejected for now. Both are real dependencies with a privacy surface, and neither
answers the actual question — a task that is never _scheduled_ throws no
exception and would produce no event. Worth reconsidering for genuine crashes.

#### Write the record to Firestore

Rejected. It would need a network in a headless context where Firebase may not
have restored the session, and it would turn a local diagnostic into a
server-side movement trace. `alertLogRepository` already records deliveries
server-side under the rules that govern it; this is not a second copy.

#### Store which black spots were near, or the coordinates

Rejected on privacy grounds, and asserted against in a test. A timestamped list
of "you were near a hazard" is location history however coarse, and this project
does not keep location history.

### Trade-offs

Benefits:

- The invisible failure becomes visible, with no new dependency.
- Pure core, fully tested, no device needed to verify the logic.

Costs / disadvantages:

- On-device only. Nobody but the user can see it, so it diagnoses one person's
  problem and never an aggregate one.
- Adds an AsyncStorage read-modify-write to every background invocation. Safe
  here because the OS delivers batches to a single JS context serially.

### Consequences

The copy in `backgroundRunCopy.ts` carries a constraint that is enforced by
tests: it must never claim the feature is _working_, and never diagnose a fault
it cannot establish. A stationary phone produces no runs, and telling that user
their warnings have stopped would be a false alarm about a safety feature — its
own kind of harm. The copy reports observations only.

The record is cleared on sign-out alongside the zone state and preferences
snapshot.

### Revisit When

A crash reporter is added for genuine exceptions — the two are complementary,
not alternatives. Also if the retention window (48 hours, 200 entries) proves
too short to diagnose a real report.

## DEC-004 — Per-path coverage floors instead of a single global percentage

**Date:** 2026-08-10
**Status:** Active
**Affected Areas:** `apps/mobile/jest.config.js`, `apps/mobile/package.json`

### Context

Mobile line coverage is ~48% and that shape is deliberate: pure safety-critical
cores are covered exhaustively, presentational components and hooks are thin.
`collectCoverageFrom` was configured but no `coverageThreshold` existed, and CI
never ran with `--coverage`, so the number was descriptive and could fall
without any gate objecting.

### Decision

Pin per-file thresholds on the safety-critical modules at their measured values,
plus a deliberately low global floor for everything else. Make `npm run test`
run with `--coverage` so both the local gate and CI enforce it.

### Reasoning

A global floor at 48% would be satisfied by a change that guts
`proximityEngine`'s tests and adds snapshot tests for three buttons. It would
also fight the intended shape, since every new screen drags the average down.

Attaching floors to the modules where a regression is a _safety_ regression is
the structural form of the Phase 13 lesson: that bug survived eleven phases
because 143 rules tests asserted only refusals, and nothing required that
anything assert the happy path.

These modules are pure functions over plain data, so measurement is exact and
pinning at the current value carries no flakiness risk.

### Alternatives Considered

#### A single global threshold

Rejected — see above.

#### Mutation testing (Stryker)

A stronger signal, and genuinely tempting given the Phase 13 lesson. Rejected as
disproportionate: a large new dependency and a slow gate for a project this
size. Targeted manual mutation was used instead when adding tests, to confirm
they fail against broken code.

#### Leave coverage unenforced

Rejected. An unenforced number is a description, not a gate.

### Trade-offs

Benefits:

- Protects the modules that matter without dictating a project-wide style.
- A drop is a real loss, not noise.

Costs / disadvantages:

- The list needs maintaining as modules are added.
- **The global floor is coupled to the pinned list**, which is genuinely
  surprising and has already caused one failure. See below.

### Consequences

Jest removes path-matched files from the global pool, so pinning a
well-covered file _lowers_ the global number. Adding `zoneStateStore` and
`zoneStatePersistence` moved the residual from 41.8% to 39.8% and broke a floor
that had been passing.

The rule that follows: when adding a path threshold, recompute the global from
the coverage summary with all pinned files excluded, and leave slack. Lowering
the global for that reason is expected; lowering it because a _file_ got worse
is the thing the ratchet exists to catch. This is documented at length in
`jest.config.js` because the natural reaction is to assume a regression.

### Revisit When

Screen and hook coverage rises enough that a meaningful global floor becomes
possible, or the pinned list grows large enough to be worth deriving from a
convention (for example, every file with a sibling `__tests__` entry).

## DEC-005 — Extract `runOrphanSweep` rather than run the Pub/Sub emulator

**Date:** 2026-08-10
**Status:** Active
**Affected Areas:** `functions/src/sweepOrphanedImages.ts`,
`firebase/tests/integration/orphanSweep.test.mjs`

### Context

`sweepOrphanedImages` was the only Cloud Function verified by inspection alone.
Its planning logic (`orphanSweep.ts`) is pure and well tested, but nothing
established that the plan was carried out — and the Phase 12 `bucketName()` bug
was exactly that failure: the Admin SDK resolved the wrong bucket, `getFiles()`
returned an empty list, and the sweep reported success having deleted nothing.

### Decision

Split the scheduled trigger from its body. `runOrphanSweep(nowMs?)` is exported
and returns an `OrphanSweepOutcome`; `onSchedule` is a one-line shell. Five
integration tests call it directly against the emulators. The Pub/Sub emulator
is **not** used.

### Reasoning

The Pub/Sub route was tried first and does not work. `firebase emulators:start
--only …,pubsub` does create the `firebase-schedule-sweepOrphanedImages` topic
and its subscription, and the published message _is_ delivered and matched — but
firebase-tools 15.2.1 then fails the dispatch with `Unsupported trigger
signature: http`, because a v2 `onSchedule` function is registered with an HTTP
signature the Pub/Sub path cannot invoke. Adding the emulator would have cost
every developer a download and a slower start-up in exchange for nothing.

Calling the body directly tests everything except the cron expression, which is
a one-line declaration.

The injectable clock mirrors `handleBackgroundLocations(locations, now)` in the
mobile app. It is not decoration: an object is spared for 24 hours after
creation and the Storage emulator sets `timeCreated` itself with no way to write
it, so moving the clock forward is the only way to observe a deletion without
sleeping for a day.

### Alternatives Considered

#### Run the Pub/Sub emulator and publish to the topic

Tried, and does not work in this version. Documented in the source comment so it
is not rediscovered.

#### Leave it unit-tested only

Rejected. That is precisely the state that let the Phase 12 bucket bug through.

#### Mock the Admin SDK in a unit test

Rejected: the bug being guarded against _was_ in the Admin SDK's bucket
resolution, so a test that mocks it away cannot catch it.

### Trade-offs

Benefits:

- The last inspection-only function is now covered end to end, against a real
  bucket and a real Firestore.
- No extra emulator, no slower start-up.

Costs / disadvantages:

- The cron schedule itself is still unverified. Accepted: it is one declarative
  line.
- `runOrphanSweep` is now public API for the test's benefit.

### Consequences

Function integration tests went from 8 to 13. One asserts specifically that the
sweep _sees_ objects in the bucket — without it, every deletion assertion passes
vacuously if the bucket is ever wrong again.

### Revisit When

firebase-tools gains a working scheduler trigger path in the emulator, at which
point driving the real trigger would be strictly better.

## DEC-006 — Report dependency advisories weekly rather than gate on them

**Date:** 2026-08-10
**Status:** Active
**Affected Areas:** `.github/workflows/advisories.yml`

### Context

No advisory checking existed. `npm audit` reports roughly 46 findings, all
transitive dev tooling that cannot be resolved without breaking the Expo SDK,
and the project's standing rule is "verified working, do not upgrade casually".

### Decision

A scheduled weekly workflow running `npm audit` and `pip-audit`, reporting to
the job summary and never failing the build. Deliberately not on push or pull
request, and no Dependabot.

### Reasoning

A gate that blocked pull requests on `npm audit` would block every pull request,
and the only available fix would be deleting the gate. Automated bump PRs would
fight the pinning policy. What is actually missing is _knowing when the set
changes_ — a new high-severity finding in a direct dependency deserves a
decision; the standing transitive noise does not.

### Alternatives Considered

#### Dependabot with automated PRs

Rejected: it would generate constant churn against deliberately pinned versions
in a stack where Expo dictates compatible ranges.

#### `npm audit --audit-level=high` as a blocking CI step

Rejected: makes an unrelated pull request fail because of somebody else's
advisory, which trains people to bypass the gate.

### Trade-offs

Benefits:

- Visibility with no churn and no false blocking.

Costs / disadvantages:

- Requires somebody to read it. A report nobody opens is worth nothing, and
  there is no notification wired up.

### Consequences

The high-signal step filters to `--audit-level=high --omit=dev`, so a finding
that survives both filters is in code that ships.

### Revisit When

The project gains a real deployment, at which point a blocking gate on
production dependencies becomes justifiable.

## DEC-007 — Reduce the README to a quick start and an index

**Date:** 2026-08-10
**Status:** Active
**Affected Areas:** `README.md`, `docs/running.md`, `docs/verification.md`,
`docs/what-has-been-built.md`, `docs/known-limitations.md`

### Context

`README.md` was 964 lines — larger than any file in `docs/` and larger than
`firestore.rules`. The Phase 15 acceptance gate is specifically "a new developer
can run everything from the README", and the quick start was followed by ~900
lines a first-time reader had to scroll past before discovering `docs/` existed.

### Decision

Cut to 274 lines: what this is, the disclaimer, quick start, prerequisites, a
documentation index, repository layout, stack, licence. Four sections moved to
`docs/` rather than being deleted.

### Reasoning

Nothing was lost, only relocated. The README's job is to get someone running and
point them at the rest; the material moved out is reference reading, not
first-contact reading.

### Alternatives Considered

#### Leave it

Rejected — it works against the phase gate it is meant to satisfy.

#### Delete the moved material

Rejected. `known-limitations.md` in particular is safety-relevant: it is the
honest account of what has never been verified, and the README now links it from
the opening section for that reason.

### Trade-offs

Benefits:

- The quick start is visible without scrolling past the project's history.

Costs / disadvantages:

- Four more files in `docs/`, and one more hop to reach the detail.
- Relative links in the moved content all had to be rewritten (`docs/x.md` →
  `x.md`, and repo-root paths gained `../`). Verified by a link check across
  every markdown file.

### Consequences

`docs/known-limitations.md` is now the single place that answers "what does this
not do", and is linked from the README intro rather than buried at line 795.

### Revisit When

The README drifts back over roughly 300 lines.
