# Security and logic audit — 2026-10-24

Scope: the whole repository — `apps/mobile`, `apps/admin`, `functions`,
`services/analytics`, `packages/shared-types`, `firebase/*.rules`, `scripts/`,
CI workflows. Method: attack-surface mapping, automated scans (gitleaks over full
git history, osv-scanner over both lockfiles, semgrep, bandit, pip-audit, npm
audit), then a manual trace of every entry point. Every finding below was
confirmed by reading the code; scanner output was treated as leads only.

## Attack surface

| Entry point                                  | Who can reach it                | Auth                                                |
| -------------------------------------------- | ------------------------------- | --------------------------------------------------- |
| Firestore / Storage via client SDK (mobile)  | anyone with the public web key  | Firebase Auth + `firestore.rules` / `storage.rules` |
| `deleteAccount`, `exportMyData` (callable)   | any signed-in account           | `request.auth.uid`                                  |
| `nearbyPlacesProxy` (callable, billable API) | any signed-in account           | `request.auth.uid`                                  |
| `sweepOrphanedImages` (scheduled, 03:00 UTC) | Cloud Scheduler only            | —                                                   |
| Admin `POST/DELETE /api/session`             | the internet                    | Firebase ID token → session cookie                  |
| Admin server actions (`lib/actions.ts`)      | the internet (public endpoints) | `getDashboardActor()` re-check in each action       |
| Admin pages `(dashboard)/*`                  | the internet                    | group layout guard (+ per-page checks)              |
| Analytics `POST /analyse`, `GET /jobs`       | wherever it is deployed         | static bearer token, `secrets.compare_digest`       |
| Repo scripts (`grantRole`, `seed*`, ...)     | developers                      | emulator guard / `demo-` project                    |

User input enters through: report fields and photos, profile and
emergency-contact fields, the places-proxy arguments, admin form posts, the
analytics request body. PII at rest: profiles (email, phone), emergency
contacts, report coordinates and photos (Storage), audit logs (operator
emails), and on-device caches and drafts.

## Fix notes

- **L7, partially fixed.** The rules now require a valid geohash alphabet and
  bound `users.phone`. They still cannot prove the geohash cell matches the
  coordinates (rules cannot compute a geohash), so a client can name a
  neighbouring cell to get a fresh duplicate fingerprint. The 10/day cap, the 60 s
  gap, and the analytics distance-based dedupe still bound it.
- **L10.** The CSP is `frame-ancestors 'none'` only. A script policy needs
  per-request nonces from a Next proxy, which is a change of its own.
- **L12, partially fixed.** Bumped: `next` 16.2.12 → 16.4.2, `firebase-admin`
  14.2 → 14.5 (with `@google-cloud/*`, `gaxios`, `google-gax`, …), `zod` 4.4.3 →
  4.6.7; PyPI `urllib3` 2.8.0, `h2` 4.4.1, `pyjwt` 2.15.1, `certifi` 2026.10.23.
  `npm audit fix` was tried and reverted (260 lockfile changes across the Expo
  toolchain — `DEC-014`). Remaining: Expo-tree advisories (`shell-quote`,
  `node-forge`, `@xmldom/xmldom`, `zod@3` inside `@expo/cli`, …) that need an SDK
  upgrade, and `pillow` 12.x (dev-only, via `mlxtend`).
- **M5 / B2** change native behaviour (`expo-image-manipulator` re-encode;
  keychain accessibility). Unit tests cover the code paths. The dev client needs a
  rebuild for the new native module, and both should be checked once on a device.
